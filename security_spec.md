# Security Specification — Ejar (إيجار)

## 1. Data Invariants & Master Source of Truth

1. **Dynamic Admin Governance & Per-Category Commission Singleton Invariant**: `/platformSettings/config` stores the active fallback brokerage commission (`1 <= commissionRatePct <= 50`, `commissionModel == 'one_time_brokerage'`), optional independent per-category commission percentages (`familyApartmentCommissionPct`, `hotelRoomCommissionPct`, `industrialFactoryCommissionPct`, `studentHousingCommissionPct`, `wholeHouseCommissionPct` each `int` in `1..50`), optional escrow protection fee (`0 <= escrowProtectionFeePct <= 25`), optional promotional discount (`0 <= tenantDiscountPct <= 50`), optional live FX rates (`usdRateEgp`, `sarRateEgp`, `eurRateEgp`, `aedRateEgp` in `1..1000`), optional live broadcast banner (`announcementText <= 300`), master switches (`allowNewListings`, `allowNewBookings`), and bounded `removedShowcaseIds` (`size <= 50`). It contains zero PII (`updatedByUid` only), allows public `get` (`list: if false`), and is writable exclusively by the bootstrapped verified Platform Admin (`12mohamed01234@gmail.com` with `email_verified == true`). `activeCommissionRateForCategory(cat)` resolves the category's dedicated percentage from `/platformSettings/config`, falling back to `commissionRatePct`, or `10` when `/platformSettings/config` does not yet exist.
2. **Real-Time User Ban & Anti-Abuse Invariant**: `/bannedUsers/{userId}` stores zero PII (`userId`, public `displayName`, `reason`, `hideListings`, `bannedByUid`, `createdAt`, `updatedAt`), is writable exclusively by `isBootstrappedAdmin()` with a self-ban lockout guard (`userId != request.auth.uid`), allows public `list` strictly when `existing().hideListings == true` (with zero `get()`/`exists()` inside `allow list`), and blocks banned users (`isNotBanned()`) from creating or updating listings, bookings, rental requests, reviews, favorites, or KYC submissions.
3. **Atomic Mandate, Whole-House & Multi-Sector Listing Invariant**: No `/apartments/{apartmentId}` document can be created unless `isNotBanned()`, `areNewListingsAllowed()`, its companion `/apartments/{apartmentId}/legalDocs/dossier` document is created atomically in the exact same batch (`existsAfter`), `commissionRatePct == activeCommissionRateForCategory(incoming().category)`, `mandateAccepted == true`, and sector-specific invariants hold (`hotel_room` or `whole_house` daily rate when `daily_or_monthly`, `studentBedsCount` & `studentPricePerBedEgp` when student beds are offered, and `houseApartmentsCount >= 1` when `category == 'whole_house'`). Verified Platform Admin can edit, hide, approve, or permanently delete any listing and its dossier.
4. **Dual PII Split Isolation Invariant (Landlords & Tenants)**:
   - Public `/apartments/{apartmentId}`, `/reviews/{reviewId}`, and `/bannedUsers/{userId}` contain zero PII. Landlord PII resides strictly in `/apartments/{apartmentId}/legalDocs/dossier`, readable only by the parent unit's `ownerId` (via Master Gate `get()`) or the verified Platform Admin.
   - Tenant verification status in `/tenantVerifications/{userId}` contains zero National IDs or phone numbers, while sensitive tenant KYC credentials reside strictly in `/tenantVerifications/{userId}/privateDocs/kyc`, readable only by `request.auth.uid == userId` (verified via Master Gate) or the verified Platform Admin, with `list: if false`.
5. **Self-Verification Prevention (Listings & Tenant KYC)**: Non-admin landlords creating a unit and tenants submitting KYC must set `verificationStatus == 'pending_review'`. Only the verified Platform Admin can transition `verificationStatus` to `'verified'` or `'rejected'`.
6. **One-Time Per-Category Brokerage Commission & Atomic Listing Deletion Invariant**: Every `/bookings/{bookingId}` creation must satisfy `isNotBanned()`, `areNewBookingsAllowed()`, `bookingId == incoming().apartmentId`, reference an existing verified `/apartments/{bookingId}` (`exists()`), atomically delete `/apartments/{bookingId}` in the exact same batch (`!existsAfter()`), match the parent unit's `ownerId` and sector rate (`monthlyRentEgp`, `dailyRateEgp`, or `studentPricePerBedEgp * bedsBooked`), match `commissionRatePct == activeCommissionRateForCategory(incoming().category)`, and enforce one-time brokerage commission math: `totalRentEgp == unitPriceEgp * unitsCount`, `platformCommissionEgp == (unitPriceEgp * commissionRatePct) / 100`, and `landlordNetEgp + platformCommissionEgp == totalRentEgp`.
7. **Rental Request Lifecycle & Terminal State Invariant**: `/rentalRequests/{requestId}` can only be created by an unbanned verified `tenantId` when `areNewBookingsAllowed()` in `'pending_approval'` or `'awaiting_payment'` state (never self-created as `'approved'`) with `commissionRatePct == activeCommissionRateForCategory(incoming().category)`. Transition to `'approved'` by a tenant strictly requires atomic existence (`existsAfter` + `getAfter`) of the paid `/bookings/{apartmentId}` document owned by `tenantId`. Terminal states (`'approved'` and `'cancelled'`) are locked against non-admin mutation.
8. **Anti-Spam Relational Notification Invariant**: `/notifications/{notificationId}` contains zero PII, enforces `recipientId == request.auth.uid || isBootstrappedAdmin()` on `get` and `list` (with zero `get()`/`exists()` inside `list`), mandates `actorId == request.auth.uid` and `isRead == false` on creation, and blocks cross-user notification spam unless `isBootstrappedAdmin()` or a verified counterparty relationship exists via `existsAfter` + `getAfter` on the referenced `/rentalRequests/{id}` or `/bookings/{id}`. Updates on notifications are strictly restricted to `['isRead', 'updatedAt']` by the recipient.
9. **Verified Tenant Review & Favorite Isolation Invariant**: `/reviews/{reviewId}` requires `isNotBanned()`, `reviewId == incoming().bookingId`, and a matching `/bookings/{reviewId}` owned by `request.auth.uid`. `/favorites/{favoriteId}` enforces `isNotBanned()`, `userId == request.auth.uid`, and deterministic `favoriteId == userId + '__' + apartmentId`.
10. **Immutable Admin Activity Log Invariant**: `/adminActivityLogs/{logId}` stores PII-free audit records of sensitive administrative actions (`commission_change`, `settings_change`, `user_ban`, `user_unban`, `listing_removed`, `listing_status`, `listing_edited`, `moderation_action`), restricted exclusively to `isBootstrappedAdmin()` on `get`, `list`, and `create` (`actorUid == request.auth.uid` and `createdAt == request.time`), with `allow update, delete: if false;` to guarantee tamper-evident transparency.
11. **Zero-PII Completed Booking Demand Signal Invariant (Heatmap)**: `/bookingDemandSignals/{bookingId}` stores strictly anonymized spatial demand coordinates (`bookingId`, `apartmentId`, `category`, `governorate`, `district`, `lat`, `lng`, `unitsCount`, `totalRentEgp`, `status == 'completed'`, `createdAt`, `updatedAt`) with zero user IDs, names, or payment references. Public `list` is allowed strictly when `existing().status == 'completed'` (zero `get()`/`exists()` inside `allow list`). Creation requires `isVerifiedUser()`, `isNotBanned()` (or `isBootstrappedAdmin()`), and relational proof via `existsAfter` + `getAfter` on `/bookings/$(bookingId)` confirming `status == 'completed'`, matching `apartmentId`, `governorate`, `totalRentEgp`, and `tenantId == request.auth.uid || isBootstrappedAdmin()`, preventing fabricated demand hotspots.

## 2. The "Dirty Dozen" Adversarial Payloads

1. **Payload 1 — Identity Spoofing on Property Creation**: `attacker_1` creates `/apartments/apt_spoof` with `ownerId: "victim_uid"`. -> `PERMISSION_DENIED`
2. **Payload 2 — Orphaned Listing Without Legal Dossier**: Landlord creates `/apartments/apt_orphan` without atomic `/apartments/apt_orphan/legalDocs/dossier`. -> `PERMISSION_DENIED`
3. **Payload 3 — Self-Verified Listing Escalation**: Non-admin landlord creates `/apartments/apt_selfver` with `verificationStatus: "verified"`. -> `PERMISSION_DENIED`
4. **Payload 4 — Unauthorized Global Settings or Ban Tampering**: Non-admin user attempts to write `/platformSettings/config` or ban another user in `/bannedUsers/{uid}`. -> `PERMISSION_DENIED`
5. **Payload 5 — Shadow Ghost Field Injection**: Landlord updates `/apartments/apt_seed` adding `{ isFeaturedGhost: true }`. -> `PERMISSION_DENIED`
6. **Payload 6 — Admin Email Spoofing (Unverified Token)**: Attacker with `{ email: "12mohamed01234@gmail.com", email_verified: false }` attempts to read `legalDocs/dossier`, approve KYC, or ban a user. -> `PERMISSION_DENIED`
7. **Payload 7 — Landlord & Tenant PII Blanket Read Attack**: Authenticated stranger calls `getDoc` on `/apartments/apt_seed/legalDocs/dossier` or `/tenantVerifications/tenant_1/privateDocs/kyc`. -> `PERMISSION_DENIED`
8. **Payload 8 — Tenant Self-Approving KYC Identity**: Tenant creates or updates `/tenantVerifications/tenant_1` with `verificationStatus: "verified"`. -> `PERMISSION_DENIED`
9. **Payload 9 — One-Time Commission Theft or Non-Deleting Booking**: Tenant creates `/bookings/apt_seed` with altered `platformCommissionEgp` or without deleting `/apartments/apt_seed`. -> `PERMISSION_DENIED`
10. **Payload 10 — Unverified Rental Request Self-Approval Without Escrow Payment**: Tenant creates or updates `/rentalRequests/req_1` to `status: "approved"` without a paid `/bookings/{apartmentId}` document. -> `PERMISSION_DENIED`
11. **Payload 11 — Banned User Write Bypass & Admin Self-Ban Lockout**: A user present in `/bannedUsers/{uid}` attempts to create a listing, rental request, or review, OR Admin attempts to ban their own `uid`. -> `PERMISSION_DENIED`
12. **Payload 12 — Cross-User Notification, Request, Favorite & KYC Scraping**: Authenticated user attempts blanket `getDocs` on `/notifications`, `/rentalRequests`, `/bookings`, `/favorites`, `/tenantVerifications`, or unhidden `/bannedUsers` belonging to others. -> `PERMISSION_DENIED`
